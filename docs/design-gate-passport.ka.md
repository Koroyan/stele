## 0. მოკლედ

**პრობლემა.** Gate v2-ში ყოველი ინვესტორისთვის, ყოველ დოკუმენტზე იქმნება ცალკე `AccessPass` ანგარიში (233 ბაიტი). მისი rent-ის დეპოზიტი — **2,512,560 lamports (~$0.38)** — Stele-ის relayer-ს უჯდებოდა, ბილინგი კი მხოლოდ 1 კრედიტს (~$0.0045–0.0075) იღებდა. ყოველი ახალი ინვესტორი Stele-ისთვის ზარალი იყო, დეპოზიტი კი სამუდამოდ იკეტებოდა (დახურვის ინსტრუქცია არ არსებობდა).

**გადაწყვეტა.** **პასპორტი:** ერთი ანგარიში ერთ საფულეზე, მთელი Stele-სთვის — ყველა კომპანიის ყველა დოკუმენტი, რომელსაც საფულე დაეთანხმა, ერთ დალაგებულ სიაში.

## 1. მიზნები და არა-მიზნები

### მიზნები

1. **ზარალის აღმოფხვრა:** Stele-ს არ უნდა დაუჯდეს მომხმარებლის მდგომარეობის (state) rent.
2. **ულიმიტო მასშტაბი:** ფასი და შემოწმების ღირებულება არ უნდა იყოს დამოკიდებული მომხმარებლების საერთო რაოდენობაზე; ერთმანეთის ტრანზაქციები არ უნდა ბლოკავდნენ.
3. **უფასო შემოწმება:** დაცულ მოქმედებას (`deposit` და ა.შ.) შემოწმება ფის არ უნდა უმატებდეს.
4. **სიმარტივე დეველოპერისთვის:** ერთი ფუნქცია, ერთი დამატებითი ანგარიში, რომლის მისამართიც საფულიდან გამოითვლება.
5. **სამართლიანი დეპოზიტები:** ყოველი დეპოზიტი ბრუნდება იმას, ვინც გადაიხადა — არასდროს სხვას.
6. **უსაფრთხოება:** on-chain კოდი მცირე, ყოველი ჩანაწერი ისეთივე სანდო, როგორიც თანხმობის ხელმოწერა.
7. **დამოუკიდებლობა:** მუშაობს Stele-ის სერვერების გარეშე; გარე სერვისები (ინდექსერი, სხვა პროგრამა) საჭირო არ არის.

### არა-მიზნები

- Proof-ის (ToS თანხმობის) ჩაწერის შეცვლა — ის უცვლელია (თანხმობაზე ანგარიში არ იქმნება).
- ZK compression / Merkle-ზე დაფუძნებული pass — მომავლის ვარიანტია (იხ. §15).
- ვინაობის (KYC) დადგენა — პასპორტი ამბობს „ეს საფულე დაეთანხმა“ და არა „ვინ არის ის“.

## 2. ტერმინები

| ტერმინი | მნიშვნელობა |
|---|---|
| **holder** (მფლობელი) | საფულე, რომელმაც თანხმობას ხელი მოაწერა; პასპორტი მას ეკუთვნის |
| **პასპორტი** | Stele-ის ანგარიში მისამართზე `PDA(["passport", holder])` |

| **entry payer** | ვინც კონკრეტული ჩანაწერის დეპოზიტი გადაიხადა |
| **policy** | `GatePolicy` — „ეს მოქმედება მოითხოვს ამ დოკუმენტის ≥ N ვერსიას“ (Gate v2-დან უცვლელი) |
| **relayer** | Stele-ის (ან კომპანიის) გასაღები, რომელიც ტრანზაქციას აგზავნის და ქსელის ფის იხდის |
| **bump** | PDA-ს ერთი ბაიტი; კლიენტი ითვლის და აწვდის — პროგრამა არ ეძებს |

## 3. არქიტექტურის მიმოხილვა

```
ინვესტორი ──(ხელმოწერა შეტყობინებაზე, უფასოდ)──▶ Stele API / relayer
                                                   │  ტრანზაქცია (v0 + lookup table):
                                                   │   [compute budget] [Ed25519 შემოწმება] [record_passport_acceptance]
                                                   ▼
                                      Stele პროგრამა (Solana)
                                       1. ამოწმებს ხელმოწერას და შეტყობინებას (როგორც ყოველ თანხმობაზე)
                                       2. ხარჯავს nonce-ის ბიტს shard-ში (განმეორება შეუძლებელია)
                                       3. პასპორტში ამატებს ან ანახლებს ჩანაწერს
                                                   │
ფონდის პროგრამა (deposit) ◀── require_current_passport(passport, policy, investor)
   კითხულობს policy-ს + პასპორტს, ორობითი ძებნით პოულობს დოკუმენტს, ამოწმებს ვერსიას
```

- **Proof** უცვლელია: თანხმობის მტკიცებულება ისევ ტრანზაქციაშია (ხელმოწერა + შეტყობინება), nonce-ის ბიტი shard-შია.
- **პასპორტი მხოლოდ „საშვია“** ფონდის პროგრამისთვის. ვერიფიკაციაზე (Verify, PDF, `@stelehq/verifier`) პასპორტის არსებობა/დახურვა გავლენას არ ახდენს.
- **Gate v2 (`AccessPass`) რჩება:** არსებული ინტეგრაციები გრძელდება. ახალ ინტეგრაციებს ვურჩევთ პასპორტს.

## 4. ანგარიშის ფორმატი

### 4.1 მისამართი

```
passport = create_program_address(["passport", holder, [bump]], STELE_PROGRAM_ID)
```

- `bump` — `find_program_address`-ის კანონიკური bump. კლიენტი ითვლის, პროგრამა **ამოწმებს** (`create_program_address`, ~1,500 CU), არ ეძებს.
- პასპორტის შექმნისას bump ინახება ანგარიშში და შემდეგ ყველა შემოწმება მას იყენებს.

### 4.2 ბაიტების განლაგება (little-endian)

| offset | ზომა | ველი | აღწერა |
|---|---|---|---|
| 0 | 8 | `discriminator` | `sha256("account:Passport")[0..8]` = `[18, 61, 245, 239, 6, 15, 18, 34]` |
| 8 | 32 | `holder` | საფულე (იგივე, რაც PDA-ს seed) |
| 40 | 4 | `entry_count` | ჩანაწერების რაოდენობა `n` |
| 44 | 1 | `bump` | PDA-ს bump |
| 45 | 32 | `base_payer` | სათაოს დეპოზიტის გადამხდელი |
| 77 | 76 × n | `entries[]` | ჩანაწერები, **დალაგებული** `document`-ის ბაიტებით, **დუბლიკატების გარეშე** |

**ჩანაწერი (76 ბაიტი):**

| entry offset | ზომა | ველი | აღწერა |
|---|---|---|---|
| +0 | 32 | `document` | Stele-ის `Document` ანგარიშის მისამართი |
| +32 | 4 | `version_number` | მიღებული ვერსიის ნომერი (u32) |
| +36 | 8 | `accepted_at` | თანხმობის დრო Solana-ს საათით (Unix წამები, i64) |
| +44 | 32 | `payer` | ამ ჩანაწერის დეპოზიტის გადამხდელი |

### 4.3 ინვარიანტები (ყოველთვის ჭეშმარიტი)

1. `data.len() == 77 + 76 × entry_count`.
2. `owner == STELE_PROGRAM_ID`, `discriminator` სწორია, მისამართი = `PDA(["passport", holder, bump])`.
3. ჩანაწერები მკაცრად ზრდადი რიგითაა `document`-ის მიხედვით (ორობითი ძებნისთვის).
4. ჩანაწერს **მხოლოდ** `record_passport_acceptance` წერს, და მხოლოდ ხელმოწერის/შეტყობინების/nonce-ის სრული შემოწმების შემდეგ.
5. ჩანაწერის `version_number` მხოლოდ იზრდება (ძველზე დაბრუნება ან იგივე ვერსიის განმეორება შეუძლებელია).
6. ანგარიშზე lamports ≥ `rent(data.len())`. დეპოზიტების ჯამი = `rent(77) + n × entry_rent`; ზედმეტი (ვინმეს შემოწირული) არავის არ ეკუთვნის და არ გაიცემა ჩანაწერის წაშლისას.

### 4.4 ზომის ზღვრები

- Solana-ს ანგარიშის მაქსიმუმი 10 MiB → **~137,000 ჩანაწერი** ერთ პასპორტში. პრაქტიკაში ინვესტორს ერთეულები ან ათეულები ექნება.
- ზრდა ერთ ინსტრუქციაში: +76 ბაიტი (Solana-ს ლიმიტი 10,240 ბაიტია).

## 5. ინსტრუქციები

### 5.1 `record_passport_acceptance`

**არგუმენტები:** `nonce_index: u32`, `nonce_tag: [u8; 8]`, `issued_at: i64`, `expires_at: i64`, `passport_bump: u8`

**ანგარიშები (რიგით):**

| # | ანგარიში | mut | signer | აღწერა |
|---|---|---|---|---|
| 0 | `relayer` | ✓ | ✓ | shard-ის relayer; იხდის ქსელის ფის |
| 1 | `rent_payer` | ✓ | ✓ | იხდის ახალ დეპოზიტს და ჩაიწერება მის მფლობელად. შეიძლება იყოს იგივე, რაც relayer |
| 2 | `config` | | | `ProtocolConfig` (PDA `["config"]`) |
| 3 | `organization` | | | |
| 4 | `document` | | | უნდა ეკუთვნოდეს `organization`-ს |
| 5 | `version` | | | უნდა ეკუთვნოდეს `document`-ს და იყოს **მიმდინარე** ვერსია |
| 6 | `nonce_shard` | ✓ | | ორგანიზაციის shard |
| 7 | `passport` | ✓ | | ხელმომწერის პასპორტი (შეიძლება ჯერ არ არსებობდეს) |
| 8 | `system_program` | | | |
| 9 | `instructions_sysvar` | | | Ed25519 / secp256r1 შემოწმების წასაკითხად |

წინა ინსტრუქცია ტრანზაქციაში: Ed25519 (საფულე) ან secp256r1 (passkey) შემოწმება — როგორც ყოველ Stele-ის თანხმობაზე.

**შემოწმებები და მოქმედებები (ზუსტად ამ რიგით):**

1. `record_signed_acceptance` — ყველა ის შემოწმება, რაც `record_acceptance`-ს აქვს: ხელმოწერა Solana-ს runtime-მა შეამოწმა; შეტყობინება პროგრამა თავად აწყობს chain-ის მონაცემებიდან და ბაიტ-ბაიტ ადარებს; ვერსია მიმდინარეა; ვადის ფანჯარა სწორია; nonce თავისუფალია და იხარჯება; relayer დასაშვებია; ინსტრუქცია ზედა დონისაა (არა CPI). შედეგი: `signer` (ხელმომწერი) და `acceptance_id`.
2. `holder = signer`. **პასპორტის მისამართი გამოითვლება ხელმომწერიდან** — relayer-ს არ შეუძლია სხვისი პასპორტის დასახელება: `create_program_address(["passport", signer, passport_bump]) == passport`, თორემ `PassportMismatch`.
3. თუ `passport.owner == System Program` (არ არსებობს, ან ვიღაცამ წინასწარ ჩარიცხა lamports): `rent_payer` ავსებს დეპოზიტს `rent(77)`-მდე, `allocate(77)` + `assign(Stele)` PDA-ს ხელმოწერით, იწერება სათაო (`holder`, `count = 0`, `bump`, `base_payer = rent_payer`).
4. პასპორტის სრული შემოწმება (§4.3: owner, discriminator, სიგრძე, კანონიკური მისამართი შენახული bump-ით) და `stored_holder == signer`.
5. ორობითი ძებნა `document`-ზე:
   - **ნაპოვნია:** `version_number > არსებული` (თორემ `AccessPassAlreadyCurrent`; ნაკლები → `PassportMismatch`). განახლდება `version_number` და `accepted_at` **ადგილზე**; ზომა, დეპოზიტი და `payer` არ იცვლება.
   - **არ არის:** `rent_payer` იხდის ზუსტად `rent(len + 76) − rent(len)` = 528,960 lamports; ანგარიში იზრდება 76 ბაიტით; ჩანაწერი ჩაისმება დალაგების პოზიციაზე (`copy_within`); `payer = rent_payer`; `count += 1`.
6. event `PassportUpdated`.

**შეცდომები:** ყველა `record_acceptance`-ის შეცდომა + `PassportMismatch`, `AccessPassAlreadyCurrent`, `ArithmeticOverflow`.

**event `PassportUpdated`:** `holder, passport, organization, document, version, version_hash, version_number, acceptance_id, accepted_at, slot, deposit_payer, passport_created, entry_created`.

### 5.2 `remove_passport_entry(document: Pubkey)`

| # | ანგარიში | mut | signer | აღწერა |
|---|---|---|---|---|
| 0 | `authority` | | ✓ | holder **ან** ამ ჩანაწერის `payer` |
| 1 | `passport` | ✓ | | |
| 2 | `refund_to` | ✓ | | უნდა იყოს ზუსტად ჩანაწერის `payer` |

1. პასპორტის სრული შემოწმება (§4.3).
2. ჩანაწერის პოვნა (არ არის → `PassportEntryMissing`).
3. `authority ∈ {holder, entry.payer}`, თორემ `PassportUnauthorized`.
4. `refund_to == entry.payer`, თორემ `PassportRefundMismatch` — **დეპოზიტი ვერასდროს გადამისამართდება.**
5. ჩანაწერი იშლება (`copy_within`), ანგარიში მცირდება 76 ბაიტით.
6. ბრუნდება **ზუსტად** `rent(old) − rent(new)` (შემოწირული ზედმეტი არა).
7. event `PassportEntryRemoved {holder, passport, document, removed_by, refund_to, refunded}`.

**აზრი:** ინვესტორი ტოვებს ფონდს → ჩანაწერს შლის; ან ფონდი ხურავს ინვესტორის წვდომას → შლის იმ ჩანაწერს, რომელიც თვითონ გადაიხადა. ორივე შემთხვევაში ფული გადამხდელს უბრუნდება.

### 5.3 `close_passport`

ანგარიშები — იგივე, რაც §5.2-ში (`refund_to` = `base_payer`).

1. პასპორტის სრული შემოწმება.
2. **ყველა** დარჩენილი ჩანაწერის `payer == base_payer`, თორემ `PassportHasOtherDeposits` (სხვისი დეპოზიტები ჯერ §5.2-ით უნდა დაბრუნდეს).
3. `authority ∈ {holder, base_payer}`, თორემ `PassportUnauthorized`.
4. `refund_to == base_payer`, თორემ `PassportRefundMismatch`.
5. მთელი lamports → `refund_to`; ზომა 0; owner → System Program.
6. event `PassportClosed {holder, passport, closed_by, refund_to, entries, refunded}`.

**თანხმობის მტკიცებულება არ იკარგება:** ხელმოწერა და შეტყობინება ტრანზაქციაშია, nonce-ის ბიტი shard-შია, ვერსია `DocumentVersion`-შია. პასპორტის დახურვის შემდეგ ხელახალი თანხმობა ახალ პასპორტს ქმნის.

## 6. შემოწმება ფონდის პროგრამაში — `require_current_passport`

```rust
let granted = stele_gate::require_current_passport(
    &ctx.accounts.passport,  // stele_gate::passport_address(investor).0
    &ctx.accounts.policy,    // ფიქსირებული: #[account(address = vault.policy)]
    &ctx.accounts.investor,  // Signer
)?;
```

**ალგორითმი:**

| # | შემოწმება | შეცდომა (კოდი) |
|---|---|---|
| 1 | policy: owner = Stele, `GatePolicy` ტიპი, კანონიკური მისამართი | `InvalidPolicy` (7600) |
| 2 | `user` ხელს აწერს ტრანზაქციას | `UserNotSigner` (7601) |
| 3 | პასპორტი: owner = Stele; თუ არა — ზუსტად მომხმარებლის მისამართია? → `AccessPassMissing` (7602), სხვა → `AccessPassInvalid` (7603) | 7602 / 7603 |
| 4 | discriminator, სიგრძე = 77 + 76n, კანონიკური მისამართი შენახული bump-ით | `AccessPassInvalid` (7603) |
| 5 | `holder == user` | `AccessPassMismatch` (7604) |
| 6 | ორობითი ძებნა `policy.document`-ზე; არ არის | `AccessPassMissing` (7602) |
| 7 | `version_number ≥ policy.required_version` | `AccessPassOutdated` (7605) |

- **დაბრუნება:** `PassportAccess {organization, document, version_number, required_version, accepted_at}`.
- **სირთულე:** O(log n) — 10,000 დოკუმენტზე ~14 შედარება. ანგარიში არ დესერიალიზდება.
- **ფი:** 0. მხოლოდ CU (იხ. §11).
- **fingerprint-ის შემოწმება** (Gate v2-ის 7606) აქ არ სჭირდება: `(document, version_number)` ცალსახად განსაზღვრავს უცვლელ `DocumentVersion`-ს, რომლის hash-იც policy-მ შექმნისას აიღო.

**აუცილებელი წესი დეველოპერისთვის:** policy-ის მისამართი **ფიქსირებული** უნდა იყოს (state-ში ან კონსტანტად), არა მომხმარებლისგან მიღებული — თორემ თავდამსხმელი თავის policy-ს მიაწვდის.

**ყველაზე ცუდი შემთხვევა** (ორგანიზაციის სახელი 40, სათაური 60, ვერსიის ეტიკეტი 16, slug 32, request domain 48 სიმბოლო, compute budget-ის 2 ინსტრუქცია, ინვესტორის რეჟიმი): v0 + ALT — **ეტევა** (ტესტი `v0_transactions_with_a_lookup_table_fit_the_worst_case`).

### 12.5 რეკომენდაცია ფასებზე

- Proof: ახლანდელი ფასები რჩება (64–100% მარჟა).
- Gate, ინვესტორის რეჟიმი: 1 კრედიტი (46–68% მარჟა).
- Gate, კომპანიის რეჟიმი: 1 კრედიტი **+ დეპოზიტი კრედიტებით** (დიდი პაკეტის ფასით პირველი დოკუმენტი ~66 კრედიტი, შემდეგი ~18), რომლებიც **ბრუნდება**, როცა ჩანაწერი იშლება.

## 14. თავსებადობა, მიგრაცია, გაშვება

1. **Gate v2 რჩება:** `record_gated_acceptance` და `require_current` უცვლელია. არსებული ფონდები არაფერს ცვლიან.
2. **ახალი ფონდები** იყენებენ `require_current_passport`-ს. ერთ ფონდს შეუძლია ორივე მიიღოს (ჯერ პასპორტი, შემდეგ AccessPass).
3. **AccessPass-ის დახურვა** (დეპოზიტის დაბრუნება Stele-ს) — ცალკე ინსტრუქცია მომავალში (`close_access_pass`), რათა ძველი დეპოზიტებიც დაბრუნდეს.
4. **პროგრამის ზომა:** +~40 KB (905,800 ბაიტი). Devnet-ზე განახლებამდე program data-ს გაფართოება (`solana program extend`) დასჭირდება.
5. **თანმიმდევრობა:** ეს დოკუმენტი → დამტკიცება → PROTOCOL_SPEC §18.8 (ინგლისური) → API/SDK → Devnet upgrade (**მხოლოდ მფლობელის მკაფიო დადასტურებით**) → დატვირთვის ტესტი Devnet-ზე → Squads multisig + timelock → გარე აუდიტი → Mainnet.
